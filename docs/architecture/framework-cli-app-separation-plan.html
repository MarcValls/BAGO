Separar el Framework de sus clientes

Una autoridad común para sesión, ejecución y evidencia; varios clientes delgados para BAGO CLI, BAGO App y herramientas anfitrionas como Pi, Codex y Copilot.

Qué se estudió

El repositorio ya tiene backend, CLI, API local, frontend/Electron y material de adaptación para Copilot. El corte pendiente es definir y hacer cumplir una frontera de servicios estable que esos clientes puedan consumir sin duplicar autoridad.

Primera prueba del límite: consultar el estado de la sesión de forma solo lectura desde CLI y App, con el mismo contrato de resultado.

Mapa de responsabilidades objetivo

Los tres tipos de cliente llaman a operaciones del framework; no llevan una copia de su autoridad.

01 · AUTORIDAD

BAGO Framework

Servicios de sesión y contexto, contratos tipados, políticas, ejecución gobernada y evidencia. Conserva SessionManager y los owners canónicos.

02 · CLIENTE PROPIO

BAGO CLI

Comandos, argumentos, salida de terminal y códigos de retorno. Traduce la interacción de consola a llamadas del framework.

03 · CLIENTE VISUAL

BAGO App

React/Electron presenta estado confirmado y solicita acciones por API. DOM y accesibilidad describen la interfaz, no la autoridad del backend.

Contrato de aplicación compartido: operación · actor/sesión · entrada validada · resultado tipado · error estable · receipt de evidencia
Adaptadores de host: Pi, Codex y Copilot se conectan mediante sus superficies nativas. Cada adaptador se valida por separado; que haya skills, prompts, hooks o extensiones en el árbol no prueba que el host los cargue.

Tres inventarios que no se deben mezclar

Un probe de UI aporta observación; no actualiza por sí mismo la definición de BAGO.

Catálogo de operaciones/capacidades

Define qué funciones reconoce el producto y con qué contratos. Permanece estable durante un cambio de selector o de layout.

Effect registry e inventario de sinks

Gobiernan y detectan efectos materiales del backend. Son una frontera de seguridad distinta; no son el catálogo visual ni un listado de botones.

Probe DOM / accesibilidad

Al fallar un locator, adjunta rol, nombre, estado, fragmento accesible, selector y captura. Genera diagnóstico para reparar el smoke o adaptador.

Decisiones que guían la secuencia

  • Reutilizar /status y /session como superficie inicial; comprobar si representan un contrato de aplicación reutilizable antes de extraer paquetes.
  • Primero trazar dependencias y ownership. Evitar un “framework nuevo” que replique SessionManager, API, CLI o gateway.
  • Copilot kit se usa como evidencia y ruta de adaptación existente, no como prueba de integración en ejecución ni como código para copiar al core.
  • El inventario de sinks pertenece a auditoría de efectos materiales; no se reutiliza como catálogo de capacidades del producto ni como índice de controles de la UI.
  • El probe guarda evidencia y fallos de UI; no escribe estado de sesión, contratos ni inventarios automáticamente.
